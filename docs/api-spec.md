## 2. 共通仕様

### 2.1 リクエスト

| 項目 | 内容 |
|------|------|
| プロトコル | HTTP/1.1 (開発環境は TLS なし) |
| ベース URL | `/api` (Nginx が `/api/*` をバックエンドへ転送) |
| リクエストボディ | JSON (`Content-Type: application/json`) |
| 文字コード | UTF-8 |
| 認証 | **なし** (誰でも呼べる。認証の導入は TBD → 「8. 未確定事項」参照) |
| リクエストボディ上限 | 10MB (Nginx の `client_max_body_size`) |
| タイムアウト | 30秒 (Nginx の `proxy_read_timeout`) |

### 2.2 レスポンス

| 項目 | 内容 |
|------|------|
| `Content-Type` | `application/json; charset=utf-8` |
| 命名規則 | フィールド名は snake_case (`employee_id`, `scheduled_date`) |
| 日付 | `YYYY-MM-DD` の文字列 (例 `2026-08-27`)。時刻は持たない |
| 日時 | 現在レスポンスに含めていない。追加する場合の形式は TBD (RFC 3339 を推奨) |
| 一覧 | JSON 配列を直接返す。0件のときは `[]` (`null` は返さない) |
| ページング | **なし。** 常に全件を返す。方針は TBD |
| 文字コード | UTF-8 |

一覧をオブジェクトで包む形 (`{"items": [...], "total": 25}`) は採用していない。
ページングを入れる段階で見直す。

### 2.3 HTTP ステータスコード

| コード | 使う場面 | 実装状況 |
|--------|---------|---------|
| 200 OK | 取得・更新・生成の成功 | 使用中 |
| 201 Created | リソース作成の成功 | 未使用 (生成 API も 200 を返している) |
| 400 Bad Request | 入力が不正、前提条件を満たさない | 使用中 |
| 401 / 403 | 認証・認可の失敗 | 未使用 (認証が無いため) |
| 404 Not Found | 対象が存在しない、ルートが無い | 使用中 |
| 500 Internal Server Error | サーバ側の失敗 (DB エラーなど) | 使用中 |

### 2.4 エラーレスポンス

エラー時は次の形を返す。

```json
{ "error": "employees or areas is empty" }
```

| フィールド | 型 | 説明 |
|-----------|----|------|
| `error` | string | エラー内容。**現状は英語のメッセージがそのまま入る** |

現状の課題 (設計時に決めたいこと):

- **エラーコードが無い。** フロントがメッセージ文字列で分岐せざるを得ない。
  `{"error": {"code": "EMPLOYEES_EMPTY", "message": "..."}}` のような形にするかは TBD。
- **メッセージが英語。** 画面に出す文言はフロント側で用意する前提になっている。
- **500 のときに DB のエラー本文がそのまま出る。** 本番運用では内部情報を出さない形に変える必要がある。

### 2.5 ルーティングに関する実測挙動

Gin の既定動作なので、明示的に実装していない挙動も知っておく必要がある。

| リクエスト | 実際の応答 | 備考 |
|-----------|-----------|------|
| 存在しないパス (`GET /api/unknown`) | `404` / `text/plain` で `404 page not found` | **JSON ではない** |
| 定義と違うメソッド (`POST /api/employees`) | `404` | 405 ではない (Gin の既定) |
| 末尾スラッシュ付き (`GET /api/duties/`) | `301` で `/api/duties` へリダイレクト | クライアントによっては追従しない |

JSON 以外が返る経路があるため、フロントは**ステータスコードを見てから body を JSON として読む**。

## 4. データモデル

API のレスポンスに出てくる JSON オブジェクトの定義。DB のカラム定義は
[テーブル定義書](./table-definition.md) を参照。

### 4.1 Employee (社員)

| フィールド | 型 | 必須 | 説明 |
|-----------|----|:----:|------|
| `id` | number | ○ | 社員ID |
| `name` | string | ○ | 氏名 (例 `佐藤 一郎`) |
| `email` | string | ○ | メールアドレス |
| `department` | string | ○ | 部署名 (例 `営業部`) |
| `active` | boolean | ○ | 当番割当の対象かどうか |

```json
{
  "id": 1,
  "name": "佐藤 一郎",
  "email": "sato.ichiro@example.com",
  "department": "営業部",
  "active": true
}
```

### 4.2 Area (掃除エリア)

| フィールド | 型 | 必須 | 説明 |
|-----------|----|:----:|------|
| `id` | number | ○ | エリアID |
| `name` | string | ○ | エリア名 (例 `会議室A`) |
| `description` | string | ○ | 作業内容。未設定時は空文字 |

```json
{
  "id": 1,
  "name": "会議室A",
  "description": "机・椅子の整頓、ホワイトボード消去"
}
```

### 4.3 Duty (当番)

社員名・エリア名を含んだ平坦な形で返す。フロントが追加の問い合わせをしなくて済むようにしている。

| フィールド | 型 | 必須 | 説明 |
|-----------|----|:----:|------|
| `id` | number | ○ | 当番ID |
| `employee_id` | number | ○ | 担当社員ID |
| `employee_name` | string | ○ | 担当社員の氏名 |
| `area_id` | number | ○ | エリアID |
| `area_name` | string | ○ | エリア名 |
| `scheduled_date` | string | ○ | 実施予定日 (`YYYY-MM-DD`) |
| `status` | string | ○ | 状態。「4.4 status」参照 |

```json
{
  "id": 1,
  "employee_id": 1,
  "employee_name": "佐藤 一郎",
  "area_id": 1,
  "area_name": "会議室A",
  "scheduled_date": "2026-08-27",
  "status": "pending"
}
```

### 4.4 status の値 (当番)

| 値 | 意味 | 現状 |
|----|------|------|
| `pending` | 未実施 | 生成時の初期値 |
| `done` | 実施済み | **更新する API が未実装** (#6) |
| `swapped` | 他者へ交代済み | **更新する API が未実装** (#8) |

### 5.5 POST /api/duties/generate

翌週分の当番を生成して登録する。

| 項目 | 内容 |
|------|------|
| 認証 | なし |
| リクエストボディ | **なし** (送っても無視される) |
| 生成対象期間 | 実行日の **7日後から11日後まで** の5日間 |
| 生成件数 | 5日 × エリア件数 (初期データでは 5 × 5 = 25件) |
| 割当方法 | `active = true` の社員をシャッフルし、日 × エリアの順にラウンドロビン |
| 初期状態 | `status` は全件 `pending` |

**レスポンス (200)**

```json
{ "created": 25 }
```

| フィールド | 型 | 説明 |
|-----------|----|------|
| `created` | number | 登録した当番の件数 |

**レスポンス (400)** — 有効な社員またはエリアが0件のとき

```json
{ "error": "employees or areas is empty" }
```

**レスポンス (500)**

```json
{ "error": "..." }
```

```bash
curl -X POST http://localhost:8080/api/duties/generate
```

**既知の制約** (基本設計書「6. 制約事項」と対応):

| # | 内容 |
|---|------|
| 1 | 土日祝を除外しない。単純な連続5日を対象にする |
| 2 | 既存の当番を消さずに追記する。**複数回実行すると同じ日・同じエリアの当番が重複する** |
| 3 | 過去の担当回数を考慮しないため、公平性はシャッフル頼み |
| 4 | 冪等ではない。リトライすると二重登録になる |

設計時に決めたいこと: 対象期間をリクエストで指定するか、重複時の扱い (エラーにする / 置き換える)、
冪等性の担保方法。

## 7. 検討中の API (仕様は設計時に確定させる)

以下は枠だけ用意したもの。**実装されていない。** 決まった内容をここに書いてから実装する。

### 7.1 PATCH /api/duties/{id} — 当番の状態更新

| 項目 | 内容 |
|------|------|
| 目的 | 当番を実施済みにする (完了報告) |
| 状態 | 検討中。実装手順書「5. ワークスルー」で例として扱っている形が候補 |

**リクエスト (案)**

| 位置 | 名前 | 型 | 必須 | 説明 |
|------|------|----|:----:|------|
| パス | `id` | number | ○ | 当番ID |
| ボディ | `status` | string | ○ | `pending` / `done` / `swapped` |

```json
{ "status": "done" }
```

**レスポンス (案)**

| ステータス | ボディ | 条件 |
|-----------|--------|------|
| 200 | `{"id": 1, "status": "done"}` | 更新成功 |
| 400 | `{"error": "invalid status"}` | id や status が不正 |
| 404 | `{"error": "duty not found"}` | 当番が存在しない |

**決めること**

| 論点 | 選択肢 |
|------|--------|
| 誰が更新できるか | 本人のみ / 全員 (認証が無い現状では区別できない) |
| `status` 以外を更新できるか | 担当者の変更を許すか、それは交代申請 (#7) に寄せるか |
| 完了日時を記録するか | 記録するなら `duties` に `done_at` 列の追加が必要 |
| 応答に更新後の Duty 全体を返すか | `{"id","status"}` だけか、[Duty](#43-duty-当番) 全体か |

### 7.2 POST /api/duties/{id}/swap-requests — 交代申請の作成

| 項目 | 内容 |
|------|------|
| 目的 | 当番を他の社員に交代してもらう申請を出す |
| 状態 | 検討中。`swap_requests` テーブルは既に存在する (未使用) |

**リクエスト (案)**

| 位置 | 名前 | 型 | 必須 | 説明 |
|------|------|----|:----:|------|
| パス | `id` | number | ○ | 交代対象の当番ID |
| ボディ | `to_employee_id` | number | ○ | 交代を依頼する相手 |
| ボディ | `from_employee_id` | number | TBD | 依頼元。認証が入れば不要になる |
| ボディ | `comment` | string | — | 依頼メッセージ。列の追加が必要 |

**レスポンス (案)**: `201` または `200` で作成した申請を返す。形は TBD。

**決めること**

| 論点 | 選択肢 |
|------|--------|
| 依頼元の特定方法 | ボディで受け取る / 認証情報から取る |
| 同じ当番への重複申請 | 許す / 承認待ちが1件でもあれば 409 |
| 相手の承認が必要か | 相手の承認のみ / 管理者の承認も必要 |

### 7.3 PATCH /api/swap-requests/{id} — 交代申請の承認・却下

| 項目 | 内容 |
|------|------|
| 目的 | 交代申請を承認または却下する |
| 状態 | 検討中 |

**リクエスト (案)**: `{"status": "approved"}` (`approved` / `rejected`)

**決めること**

| 論点 | 選択肢 |
|------|--------|
| 承認時に当番をどう変えるか | `duties.employee_id` を書き換える / 元の当番を `swapped` にして新しい当番を作る |
| 誰が承認できるか | 依頼された本人のみ / 管理者も可 |
| 却下後の再申請 | 許す / 同じ相手には不可 |

### 7.4 GET /api/reports/summary — 集計

|------|------|
| 目的 | 完了率や社員別の担当回数を出す |
| 状態 | 検討中 |

**決めること**: 集計期間の指定方法、返す指標 (完了率 / 社員別回数 / エリア別回数)、
レスポンスの構造、フロントでの表示方法。
